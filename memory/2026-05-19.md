# 2026-05-19 — Mini V2 Async Job Architecture Implementation

## Mission: Fix Mini V2 Frontend/Backend Timeout Mismatch

### Problem
- Mini V2 generation takes 105-136 seconds (first-pass + repair)
- Frontend timeout was 60s, increased to 180s
- Browser still times out before backend completes
- Users don't care about wait time, they need reliable completion

### Root Cause
Synchronous long-polling doesn't work for multi-minute generation. Browsers don't like 3+ minute requests.

### Solution Architecture: Async Job Polling

**Pattern:**
1. User submits assessment
2. Backend immediately returns job_id
3. Backend continues generation asynchronously
4. Frontend polls every 3 seconds for status
5. When complete, frontend renders report

**Storage:** Vercel Redis (Upstash integration)
- `REDIS_URL` environment variable configured
- `@vercel/kv` package installed (commit `2ea16f9`)
- 24-hour job expiration

### Implementation Files Created

**1. Job Manager (`api/engine/miniV2JobManager.js`)**
- Job state tracking (received → generating → repair → rendering → complete)
- Redis storage operations
- User-friendly progress messages
- 24-hour job TTL

**Job states:**
- received
- first_generation_running
- first_generation_complete
- repair_needed
- repair_running
- repair_complete
- rendering
- complete
- failed

**2. Start Endpoint (`api/moremindmap/mini-profile-v2-start.js`)**
- Validates answers
- Creates job record
- Returns job_id within ~2 seconds
- Starts async generation (fire-and-forget)

**3. Status Endpoint (`api/moremindmap/mini-profile-v2-status.js`)**
- Polls job status from Redis
- Returns progress or final HTML
- Frontend calls every 3 seconds

**4. Async Generator (pending creation)**
- Wraps existing generation pipeline
- Updates job state throughout execution
- Stores final HTML in job record
