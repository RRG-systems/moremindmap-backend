## ARCHITECTURAL DECISION: Three-Layer Baby Tracking (20:10 MST)

**Decision:** Move toward Option C (single source of truth) via Option A (immediate fix).

### Architecture
1. **baby_registry** (persistent JSONL) — Authoritative for identity/lifecycle
   - variant_id, parent_id, generation, dna, status, spawned_at, promoted_at
   
2. **unified_ledger** (persistent) — Authoritative for performance
   - trades with trader_id, PnL, win_rate, metrics
   
3. **evolution_engine.babies[]** (runtime cache) — Temporary only
   - May be cleared/rebuilt without losing state
   - NOT authoritative

### Implementation Path
- ✅ baby_registry.py created (registry class with load/save)
- ⏳ Wire registry into moltmarket_dashboard initialization
- ⏳ Modify execute_baby_variant() to register baby on first trade
- ⏳ Modify /api/nursery/promote to read from registry + ledger (not evolution_engine.babies)
- ⏳ Modify /api/nursery/leaderboard to read performance from ledger + status from registry

### Why This Works
- **No more sync inconsistencies:** Each layer has single source of truth
- **Ledger is performant:** Already tracking every trade, can compute PnL instantly
- **Registry is minimal:** Just identity + lifecycle, lightweight
- **Runtime cache is safe:** Can clear evolution_engine.babies[] without losing data

### Critical Insight
"Two independent sources of truth create future inconsistencies." — D.J.

This is THE architecture pattern for multi-system coordination.

## DEGRADATION ANALYSIS & FIX (20:30 MST)

### What Happened
**Last night (Apr 25):** All systems in sync
- Leaderboard: reads from evolution_engine.babies
- Promotion: reads from evolution_engine.babies
- Same source = no mismatch

**Today (Apr 26):** Architecture shifted to registry model
- Leaderboard: reads from unified_ledger (all babies with trades)
- Promotion: reads from registry (only registered babies)
- **Mismatch:** Babies not in registry yet appear in leaderboard but fail promotion

### Root Cause
When we moved to **three-layer architecture** (registry for identity, ledger for perf, runtime cache for execution):
- Babies spawned by spawn_baby_variants() live in evolution_engine.babies
- On first trade, they're auto-registered to registry
- BUT: Auto-registration happens DURING execution, not at spawn time
- **Result:** Leaderboard sees babies in ledger BEFORE registry sees them

### The Fix Applied Tonight
1. **sync_registry_with_evolution_engine()** — On startup, register all pre-spawned babies
   - Ensures registry has all babies before loop starts
   - Prevents the "leaderboard ahead of registry" problem

2. **Protected CALIBRATION mode** — BRAIN stays in CALIBRATION even if trading_enabled check fails
   - Prevents FLAT override of promotion's CALIBRATION state

### Remaining Timing Issue
- Leaderboard called at time T
- Metrics updated at time T+ΔT  
- Promotion called at time T+2ΔT
- **Result:** Leaderboard sees snapshot 1, promotion sees snapshot 2 (stale data)

### Next Session Fix (20 mins)
Create **ledger_metrics_cache** in update_metrics():
- When metrics_loop runs, fetch all baby metrics once
- Cache them in dashboard_state['_ledger_cache']
- Both leaderboard and promotion read from cache
- Eliminates timing skew, guarantees consistency

**Code pattern:**
```python
# In update_metrics()
if unified_ledger:
    all_baby_metrics = {}
    for baby_id in [b['variant_id'] for b in evolution_engine.babies]:
        all_baby_metrics[baby_id] = unified_ledger.get_trader_metrics(baby_id)
    dashboard_state['_ledger_cache'] = all_baby_metrics

# In leaderboard & promotion
ledger_metrics = dashboard_state.get('_ledger_cache', {}).get(variant_id, {})
```

### Why We Degraded
We solved the logical architecture problem (single source of truth) but introduced a **timing problem** (reading at different moments).

The lesson: When refactoring multi-system coordination, timing consistency is as important as logical consistency.
